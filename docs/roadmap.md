### 几条贯穿全局的设计原则

这些原则来自现有架构，新功能都要遵守，否则会破坏已有的正确性或成本控制：

1. **一切能力都是 action。** `ctx.actions.define()` 是控制台 API 和 Agent 工具的共同来源。新功能（指令、人格、存储浏览、测试、知识库、本地模型）都先定义 action，界面和 Agent 自动同时可用。
2. **Agent 的系统提示和工具列表在会话内不变。** `plugin-agent/src/prompt.ts` 明确要求系统提示逐字节不变，工具列表在 `createSession()` 时冻结，以保证缓存命中和 Anthropic 思考块的有效性。所以“页面场景”“技能”“推荐”都必须放进**用户消息里的 `<context>`**，不能改系统提示，也不能在会话中途增减工具。
3. **页面上的推荐默认不调用大模型。** 进入页面时的展示和推荐由本地规则算出，用户点了才发给 Agent，避免一打开页面就消耗 Token。
4. **插件可贡献、可卸载。** 技能、指令、推荐项、流程模板、结构化消息组件、存储驱动都做成注册表，插件卸载时自动移除（和 `actions.define` 一样用 `ctx.effect`）。

## 1. Agent 管理页

### 价值

现在 Agent 的行为全部写死在 `SYSTEM_PROMPT` 和 `AgentDock.vue` 的三条建议里。用户无法：

- 调整某个页面上 Agent 的提示和推荐；
- 给 Agent 增加可复用的“技能”（一段做事方法）；
- 接入外部工具（MCP）；
- 控制哪些工具可以自动执行、哪些需要确认；
- 预览 Agent 能输出的富消息样式。

管理页把这些集中到一处，也是第 2 项的数据来源。

### 页面结构（`/agent`，左侧导航新增“智能体”）

| 标签页 | 内容 |
| --- | --- |
| **场景** | 每个页面一张卡：Bots、Bot 详情、Providers、Flows、Flow 编辑器、Plugins、Logs、Overview。每张卡可配置：场景提示（拼进 `<context>`）、欢迎语、推荐项列表、默认推荐的技能、是否自动展示 |
| **技能** | 技能列表（内置 / 插件提供 / 用户自建），可新建、编辑、启用、停用，标签显示来源 |
| **MCP** | MCP 服务器列表：stdio 命令或 HTTP 地址、环境变量、状态、暴露的工具；每个工具可单独开关 |
| **工具策略** | 所有 action 的表格：名称、来源插件、风险等级、策略（自动 / 需确认 / 禁用）。可按插件、风险筛选 |
| **模型与限制** | 现有 `plugin-agent` 的 Config（提供商、模型、最大步数、确认超时）搬到这里，加每日 Token 预算 |
| **消息样式** | 结构化消息示例库，见下文 |

### 关键设计

**技能（Skill）**

- 一个技能 = 名称、描述、触发说明、正文（Markdown 做事步骤）、可选的推荐工具列表、适用场景标签。
- 存储：`data/agent/skills/<id>.json`；插件可用 `ctx.agent.defineSkill()` 贡献内置技能（例如 plugin-flows 贡献“搭建签到流程”技能）。
- 使用：用户在输入框用 `$` 选中技能后，技能正文作为 `<skill name="...">…</skill>` 块拼进**这一轮的用户消息**，不碰系统提示，缓存不受影响。

**MCP**

- 新插件 `@mushin/plugin-mcp`：作为 MCP 客户端连接服务器，把每个 MCP 工具注册成 action，命名 `mcp.<server>.<tool>`，风险等级默认 `write`，可在工具策略里改。
- 因为走的是 action 注册表，MCP 工具自动成为 Agent 工具，**也能在流程里通过新的 `action.call` 节点调用**。
- 工具列表冻结规则不变：新接入的 MCP 工具对**新会话**生效，旧会话标题处显示“工具已更新，开新对话可用”的提示。

**工具策略**

- Agent 配置新增 `toolPolicy: Record<actionName, 'auto' | 'confirm' | 'off'>`。
- `off` 的工具在建会话时就不放进工具列表；`confirm` 让 `write` 级 action 也走现有的确认流程（`waitForApproval` 已有，复用即可）。

**结构化消息**

现在 `AgentDock.vue` 只把文本按 `pre-wrap` 显示，不渲染 Markdown。计划：

1. 先接入 Markdown 渲染（markdown-it + 代码高亮），覆盖普通 Markdown、代码块、表格。
2. 定义几种结构化块，Agent 用带语言标记的代码块输出，前端识别后渲染为组件：

| 块 | 写法 | 渲染效果 |
| --- | --- | --- |
| 卡片 | ```` ```mushin-card ```` + JSON（标题、字段、按钮） | 资源卡片，例如新建的 Bot，按钮可跳转或触发操作 |
| 代码 | 普通 ```` ```ts ```` | 高亮 + 复制按钮 |
| 架构 / 流程图 | ```` ```mermaid ```` | 图表；对流程可以直接渲染迷你流程预览 |
| 提问 | 新的 client action `ui.ask`（选项 + 推荐项） | 选项卡片，用户点选后结果作为工具结果回到 Agent，和危险操作确认同一机制 |
| 进度清单 | ```` ```mushin-steps ```` | 勾选式步骤列表 |

3. 管理页“消息样式”标签展示每种块的示例和源码，可以“发送到 Agent 体验”——用本地假数据渲染，不调用模型。

### 实现方式

- 后端：`plugin-agent` 增加 `skills`、`profiles`（场景配置）、`toolPolicy` 三类数据和对应 action（`agent.skills.*`、`agent.profiles.*`、`agent.policy.*`）。
- 新插件 `plugin-mcp`。
- 前端：`views/AgentView.vue` + `components/agent/*`；把消息渲染从 `AgentDock.vue` 抽成 `AgentMessage.vue`，管理页和侧栏共用。
- 系统提示里加一段固定说明“可以输出哪些结构化块”，这是一次性修改，之后保持不变。

### 最终效果

用户打开“智能体”页，能看到每个页面上 Agent 会说什么、推荐什么；能写一个“排查 NapCat 连接”的技能并在任何页面用 `$` 调出；能接入一个 MCP 服务器（比如文件系统或 GitHub）并控制它的工具是否需要确认；能在“消息样式”里看到卡片、代码、图表、提问等效果。

- Q1-2 MCP 先支持 stdio 还是 HTTP（Streamable HTTP）？建议两者都做，stdio 优先。
- Q1-3 Mermaid 体积较大（约 1MB+），是否接受按需懒加载？

## 2. Agent 智能场景识别

### 价值

Agent 现在只在用户消息里收到一句“当前页面是 /flows/xxx”，界面上也没有任何场景感知。目标是让 Agent 像 Codex 一样：进到哪个页面，就知道该推荐什么；输入框里 `$` 调技能、`/` 调指令；历史可完整检索。

### 交互细节

**标题处的场景标识**

- Dock 标题“智能体”右侧显示当前场景标签，例如 `流程编辑器 · 签到流程`、`Bot · 测试机器人（离线）`。
- 标签可点击，展开“本页面 Agent 能做什么”的说明（来自第 1 项的场景配置）。

**进入页面时的自动展示**

- 空会话时，欢迎区按场景显示推荐卡片（替代现在固定的三条建议）。
- 有会话时，不打断对话，只在输入框上方显示一条可关闭的“推荐条”，例如在 Providers 页且有提供商测试失败时：“提供商 DeepSeek 测试失败，让我帮你排查？”
- 推荐由**本地规则**生成（见原则 3）：每条规则 = 场景 + 条件（例如“没有提供商”“有离线的 Bot”“流程有错误”）+ 文案 + 点击后发送的提示或调用的技能。

各页面的默认推荐示例：

| 页面 | 条件 | 推荐 |
| --- | --- | --- |
| Providers | 没有提供商 | 连接 DeepSeek / OpenAI / 本地 Ollama |
| Providers | 有测试失败的 | 排查失败原因 |
| Bots | 没有 Bot | 连接 QQ（NapCat）；试试演示机器人 |
| Bot 详情 | 离线 | 读日志诊断连接 |
| Bot 详情 | 在线、未开启任何插件 | 开启 LLM 聊天；推荐流程模板 |
| Flows | 没有流程 | 从场景模板创建（签到、关键词回复、客服分流…） |
| 流程编辑器 | 有校验错误 | 帮我修复这些问题 |
| 流程编辑器 | 无测试用例 | 为这个流程生成测试用例（第 10 项） |
| Plugins | 有加载失败的插件 | 查看失败原因 |

**`/` 指令选择器（参考 Codex 截图）**

- 输入框为空或光标前是 `/` 时，在输入框**上方**弹出浮层，样式参照截图：分组（指令 / 技能）、每行图标 + 名称 + 灰色描述、右侧来源标签（内置 / 插件名 / 个人），支持键盘上下选择、回车确认、继续输入即过滤。
- 指令分两类：
  1. **Agent 内置指令**：`/new` 新对话、`/history` 打开完整历史、`/model` 切换模型、`/status` 查看上下文用量、`/clear`、`/help`。这些在前端直接执行，不发给模型。
  2. **Bot 指令**（来自第 3 项的注册表）：例如 `/checkin`、`/score`。在哪里执行由用户的描述决定：
     - 用户指定了目标，例如“发给主人”“在 xx 群里执行 /抽奖”，就在对应 Bot 和会话里**真实执行**，回复真实发出，Agent 对话里同时显示一张结果卡片；
     - 没有指定目标时，用模拟会话试跑（优先演示沙盒 Bot，不会发到 QQ），回复只显示在 Agent 对话里。
     - 为此 Bot 设置里新增“主人”（一个或多个用户 id），Agent 和流程都可以用“主人”作为目标；Agent 新增 action `bots.commands.run`（Bot、指令、参数、目标会话，目标为空即模拟）。

**`$` 技能选择器**

- 同样的浮层，只列技能，按当前场景排序（场景推荐的技能排在前面并带“推荐”标记）。
- 选中后输入框里显示为一个技能胶囊（chip），发送时按第 1 项的方式拼入用户消息。

**完整历史**

- 现在的历史是一个 `NPopselect` 下拉，只有标题。改为：下拉保留最近 8 条，底部“查看全部”打开抽屉。
- 抽屉内：顶部是**标签筛选式搜索框**（输入文字做全文搜索，也可以选 `场景:流程`、`来源:技能`、`状态:运行中` 这样的标签，多个标签叠加），列表每项显示标题、时间、来源标签（在哪个页面发起、是否用了技能/指令）。
- 会话数据增加 `scene`（发起时的页面）和 `tags`（用过的技能、指令、涉及的资源 id）。

### 实现方式

- `plugin-agent`：`AgentSession` 增加 `scene`、`tags`；`agent.send` 增加 `skills: string[]` 参数；新增 `agent.search`（全文 + 标签）、`agent.commands`（内置 + 注册表汇总）。
- `prompt.ts`：`contextNote()` 增加场景提示和本页关键状态（例如当前流程的错误数），仍然只进用户消息。
- 前端：新增 `components/agent/CommandPalette.vue`（`/` 和 `$` 共用）、`components/agent/HistoryDrawer.vue`、`stores/agentScene.ts`（根据路由和 data store 计算场景与推荐）。
- 推荐规则表：内置规则写在前端；插件可通过新的 action `agent.recommendations` 贡献规则（返回声明式条件），第 1 项的管理页可覆盖文案和开关。

### 最终效果

打开流程编辑器，Dock 标题显示“流程编辑器 · 签到”，空会话里直接给出“修复 2 个问题”“生成测试用例”“解释这个流程”三张卡；输入 `/` 弹出和 Codex 一样的指令面板，能直接试 `/checkin`；输入 `$` 选“排查连接”技能；历史抽屉里搜“签到”并筛 `场景:流程`，一眼找到上周的对话。

### 待讨论

- ~~Q2-1 在 Agent 里调用 Bot 指令时，用哪个 Bot 执行？~~ 已定：按用户描述，指定了主人或某个群就真实执行，否则模拟试跑。
- Q2-2 页面推荐是否允许“可选的 LLM 生成推荐”（更聪明但耗 Token）？建议默认关闭。

## 3. 指令（command）节点

### 价值

现在 `/ping`、`/checkin` 这类指令是用“关键词”触发器模拟的，没有统一的指令概念，所以没有自动 `/help`、没有参数解析、Agent 也不知道有哪些指令。演示插件里的 `/help` 菜单是手写的。

### 细节

**节点与转换**

- 新节点类型 `trigger.command`：配置项为指令名、别名、描述、参数、是否显示在帮助中、权限（所有人 / 仅管理员）。
- 与 `trigger.keyword` 互相转换：
  - 在关键词节点里输入以 `/` 开头的词，编辑器提示“已转换为指令节点”，节点类型自动变成 `trigger.command`，原关键词变成指令名，其余关键词变成别名。
  - 在指令节点里去掉前缀 `/`，节点转回关键词节点。
  - 转换保留节点 id，所以引用 `{{n1.rest}}` 不会失效（两种节点都输出 `rest`）。
- 前缀可在 Bot 级别配置（默认 `/`，也可以加 `#`、`!`），指令名本身不带前缀存储。

**参数**

- 简单模式：输出 `rest`（指令后的全部文本），与关键词节点一致。
- 参数模式：用签名声明，例如 `/score <分数:number> [备注]`，输出 `args.分数`、`args.备注`，类型不对时自动回复用法说明（可关闭）。

**指令注册表**

- 新服务 `ctx.commands`（放在 plugin-bots，按 Bot 维度）：来源可以是流程中的指令节点、Bot 插件（`ctx.bot.command(...)`）、未来的其他插件。
- 提供 action：`commands.list`（可按 Bot 过滤，含来源：哪个流程/插件）。
- 自动帮助：每个 Bot 可开启内置 `/help`，按注册表生成菜单，不再需要手写。
- 冲突检测：同一 Bot 上两个来源注册同名指令时，在流程校验（`compile()`）里报警告。

### 实现方式

- `plugin-flows/src/nodes.ts`：新增 `commandTrigger`；`index.ts` 保存/加载流程时把指令节点同步到 `ctx.commands`。
- `plugin-bots`：新增 `commands.ts`，在 Session 上增加 `session.command`（解析后的指令名和参数），供各插件复用。
- 前端 `FlowNodeCard.vue` / 节点配置面板：关键词输入的转换提示，指令节点显示 `/name` 风格的标题。

## 5. 节点组合（分组）与复制粘贴

### 价值

流程变大后需要把相关节点归类、整体移动、复用。编辑器现在只支持 Ctrl+S，没有复制粘贴。

### 细节

- **创建组合**：框选多个节点 → 右键“组合”或 Ctrl+G。组合显示为**虚线框**，左上角是可编辑的组名，可选颜色。
- **操作**：拖动组框整体移动；双击组名重命名；Ctrl+Shift+G 解散；折叠组（只显示组框和对外连线，可选，后做）。
- **复制粘贴**：Ctrl+C / Ctrl+V / Ctrl+D（原地复制）。复制选中的节点和它们之间的连线；粘贴时：
  - 生成新的节点 id，并把配置和输入里的引用 `{{旧id.输出}}` 改写成新 id（只改写复制范围内的节点；指向范围外的引用保留）；
  - 复制组时连同组一起复制；
  - 剪贴板内容是 JSON，可以跨流程、跨浏览器标签粘贴，也能贴给 Agent。
- **组合模板（后续）**：把一个组保存为“片段”，出现在节点面板里，一键插入。

### 实现方式

- 数据模型：`FlowDocument` 增加 `groups?: { id, label, color?, nodeIds: string[] }[]`。引擎完全忽略组，`compile()` 只校验组里的节点存在。
- 前端：用 Vue Flow 的父节点能力（`parentNode` + `extent: 'parent'`）实现组框，组本身是一个自定义的 `group` 节点类型，仅存在于前端；保存时转换回 `groups`。
- 复制粘贴逻辑放在 `dashboard/src/flow.ts`，引用改写复用 `plugin-flows/src/refs.ts` 的解析规则（把它移到前后端共享的位置，或在前端实现同样的正则）。
- Agent 侧：`flows.update` 天然支持 `groups` 字段，Agent 也能分组。

### 最终效果

一个 30 个节点的流程可以分成“签到”“抽奖”“排行榜”三个虚线框；把“抽奖”整组复制到另一个流程，引用自动对上，直接能跑。

## 7. 持久化存储

### 价值

现在的存储是 `data/*.json` 文档加 JSONL 日志；流程变量全在内存里（重启就丢）；消息只能按日读 JSONL，无法查询和统计。Overview、测试用例、知识库都需要真正的数据库。

### 细节

**三层**

| 层 | 用途 | 实现 |
| --- | --- | --- |
| 内存 | 临时数据、`run` 变量、缓存 | 内存驱动（同一接口，方便测试） |
| 本地 | 默认 | SQLite（单文件 `data/mushin.db`） |
| 远程 | 多实例共享、云端 | PostgreSQL、MySQL、MongoDB；Supabase 作为 PostgreSQL 的一种连接方式，额外支持其 REST/Auth（后做） |

**统一接口 `ctx.database`**

- 表定义：插件声明模型（字段、类型、主键、索引），数据库插件负责建表和迁移（类似 Koishi 的 `ctx.model.extend`）。
- 查询：`get / create / upsert / set / remove / count`，支持简单条件和排序分页。
- 现有 `ctx.storage` 保留，用于配置类小文档；变量、消息、统计、测试结果、知识库迁移到数据库。

**数据库浏览页（`/database`）**

- 左侧表列表（按插件分组，显示行数），右侧数据表格：分页、排序、筛选、单元格查看 JSON、编辑（需确认）、导出 CSV/JSON。
- 顶部显示当前驱动、连接状态、文件大小；提供“备份”“切换驱动并迁移数据”。
- 只读的 SQL 控制台（仅 SQL 类驱动，默认关闭）。

### 实现方式：采用 minato（已验证）

候选方案对比：

| 方案 | 说明 | 优点 | 风险 |
| --- | --- | --- | --- |
| **A. 采用 minato（Koishi 的数据库层）** | 本身就是 Cordis 插件，驱动有内存、SQLite、MySQL、PostgreSQL、MongoDB | 体验与 Koishi 一致，驱动齐全，插件可动态 `extend` 表，省大量工作 | 维护者集中、版本跟随 Cordis rc；不含向量检索 |
| B. 自建薄封装 + Kysely | 驱动用 node:sqlite / pg / mysql2，MongoDB 单独写 | 完全可控、类型好 | 工作量大，MongoDB 要另写一套 |
| C. Drizzle ORM | 迁移工具成熟 | 生态好 | 表结构需静态声明，不适合插件动态扩展表 |

**2026-10-24 实测结果**（在隔离目录里装 `cordis@4.0.0-rc.11` + `minato@4.0.1` + `@minatojs/driver-sqlite@5.0.3` / `driver-memory`，跑建表、插入、更新、查询、统计）：

- 兼容：minato 及驱动的 peer 依赖是 `cordis ^4.0.0-rc.3`，在我们锁定的 rc.11 上 SQLite 和内存驱动的增删改查、`stats()` 都正常。
- SQLite 驱动用的是 Node 内置的 `node:sqlite`，**没有原生编译依赖**，Windows 上安装零障碍。注意 `node:sqlite` 从 Node 22.13 起才不需要实验参数，最低 Node 版本要从 22.12 提到 22.13。
- 接入要点（都是小适配）：
  1. 驱动通过 `ctx.baseUrl` 解析数据库文件路径，启动器要设置为实例目录；
  2. 驱动依赖名为 `logger` 的服务（调用 `logger.warn` 等），Mushin.js 的日志服务要提供这个形状；没有它时驱动会一直停在 pending；
  3. 插件扩展表（`ctx.model.extend`）必须在同时注入了 `model` 和 `database` 的上下文里，否则建表不会发生——这一点写进插件开发指南；
  4. 驱动配置用的是 schemastery（Koishi 的 schema 库），我们在外层用 zod 重新声明驱动配置，控制台表单保持统一。
- 不覆盖的部分：向量检索（第 8 项）需要另外处理。

**结论：采用 minato**，PostgreSQL、MySQL、MongoDB 直接用官方驱动，Supabase 走 PostgreSQL 驱动。风险在于它和 Cordis rc 的版本耦合，所以把 minato 版本和 cordis 一起锁定在 `pnpm-workspace.yaml` 的 catalog 里，升级 Cordis 时一并跑数据库测试。

- 新插件：`@mushin/plugin-database`：加载 minato 和所选驱动（驱动配置用 zod 声明），提供浏览页 action：`database.tables`、`database.rows`、`database.update`、`database.export`。
- 迁移：首次启用时把现有 JSONL 消息和 JSON 文档导入，保留原文件作为备份。

### 最终效果

默认零配置用 SQLite，变量重启不丢；在设置里切到 PostgreSQL 或 Supabase 时可一键迁移；“数据库”页面像一个轻量的 Table Plus，能看每张表、筛选、导出。

### 待讨论

- ~~Q7-1 选方案 A（minato）还是 B？~~ 已实测，采用 minato。
- Q7-2 Agent 是否可以直接读写数据库（查询消息统计很有用，但写操作风险高）？建议只开放只读查询，写操作标为 dangerous。

- 新插件 `@mushin/plugin-local-models`，按“运行时”抽象，而不是按“模型”：

### 最终效果

## 10. 测试用例

### 价值

流程越来越复杂，改一个节点可能破坏其他分支。现在只有手动的“用假消息试跑”，没有可保存、可回归的测试。

### 细节

- **测试用例** = 名称 + 步骤（一条或多条用户消息，支持多轮，用于 `等待回复` 节点）+ 上下文（私聊/群聊、用户、是否 @）+ 预设变量 + 断言。
- **断言类型**：回复等于 / 包含 / 匹配正则；经过某节点；走了某个分支；变量值；没有回复；（可选）LLM 评判“回复是否表达了 X”。
- **LLM 节点处理**：测试时可选“模拟”（给固定回复，结果确定）或“真实调用”（配合语义断言）。
- **自动生成**：
  1. 静态分析：从每个触发器出发枚举执行路径（分支节点的每个出口各一条），得到“需要覆盖的路径”；
  2. 合成输入：关键词/指令触发器直接生成匹配消息；正则用样例生成；比较节点取边界值（例如 `/score 59`、`/score 60`）；分类节点让 LLM 为每个标签写一句话；
  3. 快照：先按当前行为跑一遍，把结果记成预期，用户确认后保存（快照测试）；
  4. 覆盖率：编辑器里高亮未被任何用例覆盖的节点。
- **运行**：流程编辑器底部 “日志” 旁新增 “测试” 标签，显示用例列表、通过/失败、差异；保存流程时可选自动运行。
- **自动化任务**：测试运行是第 12 项通用任务系统里的一种任务；失败时通知（日志、Agent 提示、可选发消息给主人）。CLI 增加 `mushin test` 供 CI 使用。

### 实现方式

- `plugin-flows`：新增 `tests.ts`（用例存储、路径枚举、输入合成、断言），action `flows.tests.list / create / update / delete / generate / run`。复用现有 `flows.test` 的模拟会话；多轮步骤需要让模拟会话支持后续消息投递给 `等待回复` 节点。
- `plugin-tasks`：任务存储、cron 解析、运行记录；action `tasks.*`。

## 12. 自动化任务（通用调度 + 本地 CLI）

> 由第 10 项拆出。确认为通用任务系统，并要求能调用本地命令行程序。

### 价值

把“什么时候、做什么、做完通知谁”变成可配置的任务：定时跑测试、定时发消息、定时备份，以及驱动本机上的其他程序。典型场景：启动 BetterGI 的自动任务（一条龙、自动秘境等），BetterGI 跑完后发出通知，Mushin.js 收到后用 Bot 私聊告诉主人“今日任务已完成”，并附上截图或结果。

### 细节

**任务 = 触发 + 步骤 + 通知**

| 部分 | 选项 |
| --- | --- |
| 触发 | 定时（cron，如“每天 4:05”）、间隔、手动、事件（Bot 上线、流程失败、收到 Webhook、本地进程退出）、指令（例如主人私聊 `/bgi 一条龙`） |
| 步骤 | 调用任意 action（发消息、跑测试、备份数据库…）、运行流程、**运行本地命令**、等待（等待 Webhook / 进程退出 / 一段时间，带超时） |
| 通知 | 发给主人或指定群；成功、失败、超时分别配置文案；可附带命令输出的最后几行或 Webhook 带来的图片 |

**运行本地命令**

- 配置：可执行文件路径、参数、工作目录、环境变量、超时、是否以分离模式运行（启动后不等它结束）。
- 输出：stdout/stderr 实时进入任务日志，可在后续步骤里引用 `{{step1.exitCode}}`、`{{step1.output}}`、`{{step1.lastLine}}`。
- 可选“输出匹配”：stdout 出现某个正则时触发后续步骤（适合没有通知功能的程序）。
- 安全：这是能在本机执行任意程序的能力，所以
  - 新增和修改“运行本地命令”的任务是 `dangerous` 级操作，Agent 创建时必须经用户确认；
  - 运行时只执行已保存的命令，Agent 不能临时拼命令执行；
  - 可在配置里设置允许的可执行文件白名单（默认空 = 只允许控制台里手动添加的命令）。

**接收外部通知（Webhook 入口）**

- 每个任务或流程可以生成一个入口地址 `http://<mushin>/api/hooks/<id>?token=…`，外部程序 POST 过来即触发。请求体（JSON、表单或图片）作为变量交给后续步骤。
- BetterGI 的“通知”设置里有 Webhook 通道（具体字段在实现前对照 BetterGI 文档确认），填入这个地址即可；同样适用于其他脚本、Home Assistant、CI 等。
- 流程里对应新增触发器 `trigger.webhook`，这样“收到通知后怎么回复”也能用流程编辑器画。

**BetterGI 示例**

1. 主人私聊 Bot：`/bgi 一条龙`（指令触发任务）；
2. 步骤一：运行 `BetterGI.exe --startOneDragon`（分离模式；实际参数以 BetterGI 的命令行支持为准）；
3. 步骤二：等待 Webhook，超时 2 小时；
4. 通知：收到 Webhook 后把其中的结果和截图私聊发给主人；超时则发“BetterGI 2 小时内没有回报，请检查”。

### 实现方式

- 新插件 `@mushin/plugin-tasks`：任务存储（第 7 项完成前用 JSON 文档，之后迁到数据库）、cron 解析、运行记录（每次运行的步骤、输出、耗时）、子进程管理（插件卸载时按配置结束或保留子进程）。
- action：`tasks.list / create / update / delete / run / runs / cancel`，`hooks.create / delete`。
- `plugin-console`：新增 `/api/hooks/<id>` 路由，用单独的 hook token 校验，不需要管理员 token。
- 前端：`/tasks` 页面，任务列表 + 步骤编辑器 + 运行记录；Overview 显示“今日任务 成功 / 失败”。
- Agent：可以用自然语言创建任务（“每天早上 8 点在 xx 群发天气”），涉及本地命令时走确认。

### 最终效果

在“任务”页新建“原神一条龙”：主人发 `/bgi 一条龙` → Mushin.js 启动 BetterGI → BetterGI 完成后通过 Webhook 回报 → Bot 私聊主人“一条龙完成，用时 38 分钟”并附截图。同一个系统还负责每天凌晨跑流程测试、每周备份数据库。

## 13. 权限插件与权限检测节点

> 按讨论修订：主人（master）和管理员（admin）是两个不同的角色；权限做成独立插件，没有数据库也能用，装了数据库后再扩展。

### 价值

群管类流程（禁言、踢人、设头衔、开关功能）和群内小游戏（签到、积分、抽奖）都要先回答“这个人能不能用”。现在只有零散的做法：

- OneBot 插件的「发送者身份」节点按 master / owner / admin / member 分支，但只支持 OneBot，主人 QQ 要在每个节点里重复填写；
- P1 的指令节点有“所有人 / 仅管理员”两档，名单放在 Bot「指令」页，别的节点用不上。

做成一个权限插件后，谁是主人、谁是管理员只配置一处，流程、指令和 Bot 插件都按同一套规则判断。

### 细节

**第一阶段：不需要数据库（`@mushin/plugin-permissions`）**

- 每个机器人单独配置两份名单：**主人（master）**和**管理员（admin）**；不在名单里的都是**普通用户（user）**。
  - master：机器人的拥有者，最高权限，例如可以改机器人设置、执行危险指令；
  - admin：受信任的协助管理者，例如可以禁言、发公告，但不能改机器人设置；
  - user：其他所有人。
- 角色有高低：master ⊃ admin ⊃ user，要求 admin 的地方 master 也能通过。
- 配置位置：Bot 详情页新增「权限」标签页（P1 的「指令」页里的“管理员”名单迁移到这里，按 admin 处理），也可以在插件设置页按机器人统一编辑。
- **权限检测节点 `logic.permission`**
  - 分支：`allow`、`deny`；输出 `role`（`master` / `admin` / `user`）和 `reason`（没通过的原因）。
  - 配置：允许的角色，多选：机器人角色 master、admin、user（或填“至少 admin”），以及群身份**群主**、**群管理员**（适配器支持时才可选）。满足任一选中项即通过。节点本身不回复：没有权限时静默，只走 `deny` 分支；需要提示的话，用户在 `deny` 分支后自己接回复节点（可以用 `{{<节点>.reason}}`）。
  - 输出里另有 `groupRole`（`owner` / `admin` / `member`，私聊或适配器不支持时为空）。
  - 节点卡片标题显示摘要，例如“权限：至少 admin”。
- 指令节点的“谁可以使用”改成同样的三个角色；`bot.command()` 也接受 `role: 'admin'` 这样的要求；`/help` 可选择只列出对方能用的指令。
- 群身份（群主、群管理员）是平台概念，和机器人角色分开存放、分开判断，但都能在权限检测节点里选：
  - 适配器通过 `bot.useRoleResolver()` 声明自己能提供群身份。OneBot 先用消息里自带的 `sender.role`，事件触发（没有发送者身份）时再调用 `get_group_member_info`，结果按群和用户缓存几分钟；
  - 适配器不支持时，群主、群管理员两个选项显示为不可用，并说明当前适配器不提供群身份；流程的适配器未选定时，选项可选，但运行在不支持的机器人上时视为不满足；
  - 私聊里没有群身份，这两个选项不满足；
  - OneBot「发送者身份」节点保留，用来按群身份走不同分支。
- 流程测试增加“模拟角色”，可以分别以 master、admin、user 发送测试消息，执行日志里显示判定结果和原因。

**第二阶段：装了数据库之后（依赖第 7 项）**

- 数据库插件提供流程里的**数据库节点**（查询、写入、计数、更新），流程可以直接维护自己的数据表，例如签到记录、积分、背包。
- 权限插件在数据库里建两张表：
  - 会话成员表：某个会话（群或私聊）里的用户及其角色、标签、加入时间、备注，供“签到游戏群”这类场景维护专门的用户管理；
  - 权限规则表：针对某个会话的规则，例如“本群只有 VIP 标签能用 /抽奖”“本群禁用 /ai”“某用户在本群被拉黑”。
- 权限检测节点增加“来源”选项：
  - 机器人名单（第一阶段的 master / admin / user）；
  - 会话规则（从数据库读取当前会话的规则和成员角色、标签）；
  - 两者组合：先看会话里的拉黑和规则，再看机器人名单。
- 提供配套节点：设置会话角色、添加 / 移除标签、拉黑 / 解除拉黑，管理员可以在群里用指令管理成员，例如 `/设为管理 @某人`、`/拉黑 @某人`。
- 控制台：「权限」页增加按会话查看和编辑成员与规则的视图；数据库浏览页（第 7 项）里也能直接看到这两张表。
- 没装数据库时，这些选项和节点显示为不可用，并提示需要先启用数据库插件（依赖声明见第 14 项）。

### 实现方式

- 新插件 `@mushin/plugin-permissions`（App 插件）：
  - 服务 `ctx.permissions`：`roleOf(botId, userId, session?)`、`groupRoleOf(session)`（交给机器人的角色解析函数）、`check(rule, session)`，以及插件扩展点 `defineSource()`，第二阶段的数据库来源通过它接入；
  - 每个机器人的 master / admin 名单存放在插件自己的存储里（`ctx.storage`），第一阶段不依赖数据库；
  - 注册 `logic.permission` 节点（依赖 flows，可选）；
  - action：`permissions.get / update`（按机器人读写名单）、`permissions.check`（给 Agent 和测试用）。
- `plugin-bots`：P1 的 `commands.admins` 在启动时迁移为权限插件的 admin 名单；指令权限的判断改为调用 `ctx.permissions`（未启用权限插件时，带权限要求的指令一律拒绝并在日志里说明）。
- `plugin-bots`：新增 `bot.useRoleResolver()`，适配器注册群身份解析函数，`bots.adapters` 返回是否支持群身份，供节点配置界面判断选项是否可用。
- `plugin-adapter-onebot`：注册群身份解析（`sender.role` → `get_group_member_info`，带缓存）；「发送者身份」节点复用它。
- `plugin-flows`：`FlowSession` 增加 `role()` 和 `groupRole()`；测试输入增加 `role` 和 `groupRole`，测试面板可以模拟“群管理员”等身份。
- 第二阶段：权限插件对数据库插件声明可选依赖，检测到数据库后用 `ctx.model.extend` 建会话成员表和规则表，并注册数据库来源和配套节点。
- Agent：`flows.nodeTypes` 自动带上新节点；用户可以说“把 12345 设为这个机器人的管理员”。

### 最终效果

- 第一阶段：做一个“禁言”流程：指令 `/禁言 <QQ> [分钟:number]` → 权限检测（至少 admin）→ `allow` 分支接禁言节点，`deny` 分支接一个回复节点“只有管理员可以禁言”。普通用户会收到提示，admin 和 master 可以直接用；如果再勾选“群管理员”，QQ 群里的管理员不用加进名单也能禁言；测试面板里切换“模拟角色”就能分别验证。
- 第二阶段：签到游戏群里，`/签到` 流程用数据库节点记积分；`/抽奖` 前的权限检测读取本群规则，只有带“VIP”标签的成员能抽；群管理员用 `/拉黑 @某人` 把捣乱的人加入本群黑名单。

- ~~Q13-1 没有权限时默认静默还是回复？~~ 已定：默认静默，节点不内置回复，用户按 `deny` 分支自己加回复。指令节点没有权限时同样静默。

- ~~Q13-3 群主、群管理员要不要默认映射为 admin？~~ 已定：不映射，权限检测节点直接提供群主、群管理员选项（适配器支持时）。

## 14. 插件依赖声明

### 价值

现在插件只在代码里写 `inject`（例如流程 Bot 插件需要 `flows` 服务），缺少依赖时插件会一直停在“等待中”，界面上看不出缺了什么，也没法一键补齐。随着权限、数据库、知识库、本地模型等插件增加，依赖关系会越来越多：

- 权限插件的第二阶段依赖数据库插件，权限检测节点依赖流程插件；
- 知识库依赖数据库和嵌入模型；
- 第三方插件可能依赖某个版本以上的 Mushin.js 或其他插件。

需要把依赖写成插件清单里的声明，让控制台、插件管理器和 Agent 都能读懂。

### 细节

**清单字段（`package.json` 的 `mushin` 字段）**

```json
{
  "mushin": {
    "kind": "app",
    "provides": ["permissions"],
    "requires": {
      "mushin": ">=0.2.0",
      "plugins": { "@mushin/plugin-bots": "*" }
    },
    "optional": {
      "plugins": { "@mushin/plugin-flows": "*", "@mushin/plugin-database": ">=0.1.0" }
    }
  }
}
```

- `provides`：插件提供的服务名，例如 `flows`、`database`，用来把 `inject` 里的服务名对应到插件包；
- `requires`：必需依赖，缺少时插件不能启用；
- `optional`：可选依赖，缺少时插件照常运行，但对应功能不可用，并说明原因（例如“装上数据库插件后可按会话管理权限”）；
- `mushin`：要求的 Mushin.js 版本范围；
- Bot 插件同样适用，例如流程 Bot 插件 `requires` 流程 App 插件。

**插件管理器的行为**

- 启用插件时检查必需依赖：已安装但未启用的依赖，一并列出，确认后按依赖顺序启用；未安装的依赖，提示去安装（插件市场完成后可一键安装）；版本不满足时说明需要的版本。
- 停用插件时列出依赖它的插件，确认后一起停用；`essential` 插件仍不能停用。
- 启动时按依赖拓扑排序加载，发现循环依赖时报错并指出循环链。
- 插件状态里增加“缺少依赖”这一种，取代现在不明原因的“等待中”，并写明缺的是哪个包或服务。
- 代码里的 `inject` 与清单不一致时（例如注入了 `database` 却没声明），开发模式下给出警告，帮助第三方插件作者补齐声明。

**界面**

- 插件页：每个插件显示“依赖”和“被依赖”，缺少的依赖标红，旁边有“启用依赖”按钮；可选依赖显示为“可增强”。
- 流程编辑器：节点来自未启用的插件时，提示“启用 xx 插件后可用”，而不只是“未知节点类型”。
- 需要某个插件的功能（例如权限检测节点的“会话规则”来源），在不可用时直接说明需要哪个插件。

### 实现方式

- `core/manifest.ts`：`PluginManifest` 增加 `provides`、`requires`、`optional` 字段，读取 `package.json` 时校验格式；版本比较用 `semver`。
- `core/manager.ts`：
  - 新增依赖解析：服务名 → 提供者插件、拓扑排序、循环检测；
  - `plugins.enable` / `plugins.disable` 先返回需要连带启用或停用的插件，确认后再执行；Agent 调用时这一步走确认；
  - 新增 action `plugins.dependencies`（某个插件的依赖树和缺失项）。
- 内置插件全部补上声明，测试里校验“声明与 `inject` 一致”。
- `docs/plugin-guide.md` 增加依赖声明一节。
- 第三方插件市场（尚未实现）安装时按声明一并安装依赖。

### 最终效果

在插件页启用“权限”插件：提示“需要：机器人（已启用）；可增强：流程（已启用）、数据库（未安装）”。启用后权限检测节点可用，会话规则选项显示“安装数据库插件后可用”。停用“流程”插件时提示“流程 Bot 插件、权限检测节点将不可用”，确认后一起停用。
