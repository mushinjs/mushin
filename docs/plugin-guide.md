# Writing Mushin.js plugins

A Mushin.js plugin is a [Cordis](https://github.com/cordiverse/cordis) plugin plus a `mushin` field in its `package.json`. There are two kinds:

- **Bot plugins** change how one bot behaves. They load once for every bot that enables them, inside that bot's isolated context.
- **App plugins** extend Mushin.js itself: new actions, provider types, adapters, services.

Import everything from `@mushin/core`; it re-exports Cordis and zod.

## A bot plugin

This is the whole echo plugin (`packages/bot-plugin-echo`):

```ts
import { type Context, field, z } from '@mushin/core'
import type {} from '@mushin/plugin-bots'

export const name = 'echo'
export const inject = ['bot']

export const Config = z.object({
  prefix: z.string().min(1).default('echo ').meta(field('Prefix', 'Messages starting with this prefix are echoed back', {
    'zh-CN': { title: '前缀', description: '以此前缀开头的消息会被复读' },
  })),
})

export function apply(ctx: Context, config: z.infer<typeof Config>) {
  ctx.bot.middleware(async (session, next) => {
    if (!session.text.startsWith(config.prefix)) return next()
    await session.send(session.text.slice(config.prefix.length).trim())
  })
}
```

And its manifest:

```json
{
  "name": "mushin-bot-plugin-echo",
  "type": "module",
  "exports": { ".": "./src/index.ts" },
  "keywords": ["mushin-plugin"],
  "mushin": {
    "kind": "bot",
    "platforms": ["onebot"],
    "displayName": { "en": "Echo", "zh-CN": "复读" },
    "description": { "en": "Replies to \"echo <text>\" with the text" }
  }
}
```

What the pieces do:

- `name` labels the plugin in logs and in message provenance. Replies sent from its middleware show "Generated by: a plugin (echo)" in the live view.
- `inject` lists the services the plugin uses. Cordis 4 requires every service to be listed. `bot` is always the plugin's own bot.
- `Config` is a zod schema. Cordis validates the config with it, and the dashboard renders a form from it. `field()` adds a title, a description and translations to each field.
- `apply` registers behavior. Everything registered through `ctx` is removed when the plugin is disabled or the bot stops.

### Sessions

Middleware receives a `Session` for each incoming message:

| Member | Meaning |
| --- | --- |
| `session.text` | Plain text, with mentions of this bot removed |
| `session.segments` | OneBot-style segments (`text`, `at`, `image`, `face`, `reply`, …) |
| `session.channel` | `{ type: 'group' \| 'private', id }` |
| `session.user` | `{ id, name }` |
| `session.isDirect`, `session.mentioned` | Private chat; message @-mentions this bot |
| `session.send(content)` | Reply in the same chat |
| `session.reply(content)` | Reply quoting the incoming message |

Call `next()` to let later plugins see the message. `ctx.bot.send(channel, content)` sends outside a session, and `ctx.bot.call(action, params)` reaches raw adapter APIs, including NapCat's extensions.

### Replying with an LLM

Inject `llm` and pass the result of `ctx.llm.chat()` straight to `send`, so the reply records its provider, model and latency:

```ts
export const inject = ['bot', 'llm']

ctx.bot.middleware(async (session, next) => {
  if (!session.mentioned) return next()
  const result = await ctx.llm.chat({
    provider: ctx.bot.record.provider, // the bot's default provider, if set
    messages: [{ role: 'user', content: session.text }],
  })
  await session.send(result)
})
```

See `packages/bot-plugin-llm-chat` for a complete version with per-chat history.

## An app plugin with actions

Actions are how features reach both the dashboard and the Agent. Define one and it appears as `POST /api/actions/<name>` and as an Agent tool, with its zod schema as the tool's parameters:

```ts
import { type Context, z } from '@mushin/core'
import type {} from '@mushin/plugin-bots'

export const name = 'broadcast'
export const inject = ['actions', 'bots']

export function apply(ctx: Context) {
  ctx.actions.define({
    name: 'broadcast.send',
    description: 'Send the same text to a group from every online bot. Returns how many bots sent it.',
    risk: 'write',
    input: z.object({ group: z.string(), text: z.string().min(1) }),
    handler: async ({ group, text }) => {
      let sent = 0
      for (const info of ctx.bots.list().filter((bot) => bot.status === 'online')) {
        await ctx.bots.bot(info.id)?.deliver({ type: 'group', id: group }, text, { source: { kind: 'manual' } })
        sent++
      }
      return { sent }
    },
  })
}
```

Write descriptions for the Agent: say what the action does and what it returns. Pick the risk level carefully:

| Risk | Use for | Agent behavior |
| --- | --- | --- |
| `read` | Lists and lookups | Runs immediately |
| `write` | Creating or changing things | Runs immediately; shown as a step |
| `dangerous` | Deleting, anything hard to undo | Waits for the user to approve |

Its manifest uses `"kind": "app"`. Enable it from the Plugins page or with the `plugins.enable` action; Mushin.js adds it to `mushin.config.json`.

## Flow nodes

An app plugin can add node types to the flow editor. Inject `flows` and call `ctx.flows.defineNode()`; the node appears in the editor's palette and in `flows.nodeTypes` for the Agent, and goes away when the plugin unloads.

```ts
import { type Context, z } from '@mushin/core'
import type {} from '@mushin/plugin-flows'

export const name = 'weather-nodes'
export const inject = ['flows']

export function apply(ctx: Context) {
  ctx.flows.defineNode({
    kind: 'action',
    type: 'weather.lookup',
    category: 'data',
    title: { en: 'Weather', 'zh-CN': '天气' },
    description: { en: 'Looks up the weather for a city' },
    config: z.object({
      units: z.enum(['metric', 'imperial']).default('metric'),
    }),
    inputs: [{ name: 'city', type: 'text', title: { en: 'City', 'zh-CN': '城市' } }],
    outputs: [{ name: 'summary', type: 'text', title: { en: 'Summary', 'zh-CN': '概况' } }],
    execOut: ['found', 'unknown'],
    async run({ config, inputs, signal }) {
      const response = await fetch(`https://example.com/weather?city=${encodeURIComponent(inputs.city ?? '')}&units=${config.units}`, { signal })
      if (!response.ok) return { exec: 'unknown' }
      const data = await response.json()
      return { exec: 'found', outputs: { summary: data.summary } }
    },
  })
}
```

Pick the kind by how the node runs:

| Kind | Implement | Use for |
| --- | --- | --- |
| `trigger` | `match({ config, session, vars, event, now })` returns outputs when the run should start, or `undefined`. Set `source` to `'event'` to match adapter events (`event.name`, `event.data`) instead of messages, or to `'schedule'` with a `due(config, { now, last, since })` that says when to fire | New ways to start a flow |
| `action` | `run(context)` returns `{ exec, outputs }`; `exec` picks one of `execOut` (the first when omitted) | Every step: computing a value, calling an API, sending, waiting, branching |

`run` gets the node's parsed `config`, its resolved `inputs`, the incoming `session` (`text`, `user`, `channel`, `send`, `reply`), `vars` for variables, `llm`, a `logger`, a `signal` that aborts when the run is stopped, `bot` (`call(action, params)` for the adapter's raw API and `send(channel, content)` to any chat), the `event` that started the run if any, and `waitForMessage({ who, seconds })`. In test runs `bot.call` records the call and resolves to `null`, so handle empty responses. Adapters feed events with `ctx.bot.dispatchEvent({ type, data, name, channel, user })`; only events with a `name` reach flows. `packages/plugin-adapter-onebot/src/nodes.ts` has the OneBot triggers and API nodes as examples. Users bind each input to a reference such as `{{n1.rest}}` in the editor; inputs arrive already converted to the port's type, and references in config strings are filled in before `run`. Later nodes read your outputs as `{{<node id>.<output>}}`. Port types are `text`, `number`, `boolean`, `message` and `any`.

Reply through `session.send()` or `session.reply()` with a `source` of `{ kind: 'flow', flow: flow.name, node: node.label }` so the dashboard shows which node answered; see `action.reply` in `packages/plugin-flows/src/nodes.ts`. During a test run the session only records what would be sent, so nodes behave the same in tests. A node whose exec outputs depend on its settings, like Classify intent with one branch per label, sets `execOutFrom: { key: 'labels', extra: ['other'] }` instead of `execOut`.

Write `title`, `description` and config field descriptions for both the user and the Agent: they are what the palette, the inspector and `flows.nodeTypes` show.

## Provider types and adapters

- A provider type calls `ctx.llm.defineType({ id, displayName, config, secrets, presets, create })`. `create` returns a client with `chat()` and, optionally, `stream()` and `listModels()`. See `packages/plugin-provider-openai`.
- An adapter calls `ctx.bots.defineAdapter({ id, displayName, config, secrets, segments, plugin })`. `plugin` is loaded inside each bot's context; it opens the connection, calls `ctx.bot.useTransport()` to send, and `ctx.bot.receive()` for each incoming message. See `packages/plugin-adapter-onebot`.

## Local plugins

Put a plugin folder (with its `package.json`) in `<instance>/plugins/<name>/`, for example `instance/plugins/weather/`. Mushin.js loads TypeScript sources directly. Click **Rescan installed plugins** on the Plugins page, or ask the Agent to rescan (`plugins.catalog` with `refresh: true`), and the plugin appears in the catalog.

Plugins run in the same process as Mushin.js and can reach every service. Review third-party code before installing it.
